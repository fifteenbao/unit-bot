# 提取边界与架构

## 原工程到通用工程

| 原工程资产 | 通用版本处理 |
|---|---|
| core/plans_store.py 中的 12 阶段、标题、依赖 | 提取为 agents/registry.json，保留原顺序和依赖 |
| agents 下的角色方法 | 按原职责重写通用 prompt，去掉行业案例、固定价格和不可用工具名 |
| 主 agent 的阶段路由、统一写入 | core/cli.py + core/workflow.py |
| 单产品数据库与固定路径 | 项目配置 + 按 project id 隔离的存储 |
| 固定模型消息循环 | 任务包协议；宿主执行或外部运行器实现 |
| 七桶框架、型号/品牌、拆机推断规则 | 行业扩展，继续保留在 unit-bot |
| 材料/供应商/工艺/模具/工具私有库 | 项目资料或运行器只读接口，未复制业务内容 |
| FCC 下载与 OCR | 可选行业采集流程，不作为通用运行前提 |

这次提取以独立目录交付，原工程不依赖新核心；尚未将 unit-bot 改造成新核心的适配器。

## 数据流

项目配置 + 本地资料 + 已完成上游 → 阶段任务包 → 宿主/运行器 → 结果校验 → JSON 存储 → Markdown。

任务包包含注册顺序中此前所有仍有效的阶段结果，以便功能分析读到客户需求、体系建设读到完整研究上下文。
硬依赖决定能否执行，附加上下文决定是否需要刷新结果。因此独立阶段在补入较早的研究结果后也可能标为过期；这是保守的上下文一致性策略。

任务包指纹覆盖项目配置、资料内容、阶段定义、提示词和上游结果。
导入时重新计算指纹，拒绝跨项目、跨阶段和过期结果。
`stages.json` 是事实存储，原子替换；Markdown 是可通过 overview 命令重建的派生产物。
旧结果被重跑覆盖，目前没有完整历史版本、并发锁和人工审批状态机。

## 方法论的通用化边界

- DFA 保留九类方向，拆解保留运动/材料/装配维修要求与理由，去掉自动合并的简化判断。
- DFM 保留五类方向和 Should Cost 五要素，取消行业默认价、默认利润率及通用节省幅度。
- 功能分析要求价值和成本的可比归一化口径，阈值随项目证据说明。
- TRIZ、FOS、趋势、平台化和体系建设保留分析方法，行业结论必须重新取证。
- 总览汇集结果摘要和阶段报告链接，不自动将可能重叠的节省数值求和。

## 扩展路径

下一行业通常只需增加项目模板、成本分类、指标及只读资料接口。
若需要恢复原工程的自动联网工具循环，可在外部运行器内复用其模型/工具适配逻辑；不得让通用核心反向导入 unit-bot。
项目尚未设置开源许可证，独立发布前应由所有者明确授权条款。
